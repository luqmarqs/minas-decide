# API — contratos implementados (Worker Hono, `/api/v1`)

Fonte de verdade dos schemas: `shared/contracts/*.ts`. Implementação: `worker/`. Estado em 2026-10-09 (BE-5: autenticação Clerk, ADR 0005).

**Envelope.** Sucesso `{ data, meta: { request_id } }`; erro `{ error: { code, message, fields? }, meta }`. Status por código em `HTTP_STATUS_BY_CODE`. Zod → `VALIDATION_ERROR` com `fields` (caminho → mensagem). Nunca stack/SQL. Header `X-Request-Id` em toda resposta; `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`.

**Códigos de erro** (`ApiErrorCode`, mensagens padrão em `worker/errors.ts`):

| Código | HTTP | Quando |
|---|---|---|
| `VALIDATION_ERROR` | 400 | corpo/parâmetros inválidos (`fields`), corpo > 32 KB |
| `UNAUTHENTICATED` | 401 | sem token, token inválido/expirado, usuário banido/inexistente no Clerk; assinatura inválida no webhook |
| `FORBIDDEN` | 403 | nível insuficiente, `Origin` não permitido, conta suspensa (`PATCH /me`, QA3-06) |
| `EMAIL_NOT_VERIFIED` | 403 | e-mail principal não verificado |
| `NOT_FOUND` | 404 | recurso inexistente/oculto; webhook desativado (sem `CLERK_WEBHOOK_SIGNING_SECRET`) |
| `CONFLICT` | 409 | versão/estado divergente, e-mail já usado (cadastro e ações de organizador) |
| `UNPROCESSABLE` | 422 | regra de negócio |
| `RATE_LIMITED` | 429 | limite excedido (`Retry-After`) |
| `TURNSTILE_FAILED` | 400 | Turnstile inválido/reutilizado |
| `WRITES_SUSPENDED` | 503 | `WRITES_ENABLED !== 'true'` |
| `SERVICE_UNAVAILABLE` **(QA3-05)** | 503 | Clerk indisponível: falha de rede/JWKS ao verificar o token, ou Backend API com 429/5xx/sem resposta. Mensagem "Serviço de autenticação indisponível, tente de novo"; `Retry-After: 5`. Nunca vira 401 nem 500 |
| `INTERNAL_ERROR` | 500 | erro inesperado ou configuração inválida |

**Globais.** Ordem dos middlewares em `/api/*`: request id → **validação de configuração** (I03: `RSVP_DEVICE_SECRET` com ≥ 32 caracteres e diferente do placeholder; BE-5: `CLERK_SECRET_KEY` no formato `sk_test_…`/`sk_live_…` e `sk_live_` obrigatório com `APP_ENV=production`; QA3-04: fora de `local`/`test`, emissor do Clerk conhecido via `CLERK_ISSUER` ou `CLERK_PUBLISHABLE_KEY` decodificável; senão 500 `INTERNAL_ERROR` + log `misconfigured` só com o nome da variável) → corpo máx. 32 KB (`VALIDATION_ERROR`) → **guarda de `Origin`** (F14: POST/PATCH/DELETE com `Origin` fora de `PUBLIC_ORIGIN` + `ALLOWED_ORIGINS` → 403 `FORBIDDEN`; sem `Origin` passa; com `APP_ENV=local` qualquer origem loopback é aceita) → `WRITES_ENABLED !== 'true'` → toda mutação responde 503 `WRITES_SUSPENDED` (GETs seguem; exceção: `POST /webhooks/clerk`, que só apaga dados). Rate limit best-effort por isolate, chave `CF-Connecting-IP` (+ identidade onde indicado) e bucket (`X-Forwarded-For` é ignorado). Log estruturado por requisição: `{request_id, route, method, status, ms, rate_limited}`.

**Cache de borda (F16).** Os GETs públicos (`/territories/search`, `/territories/:id`, `/groups`, `/activities`, `/activities/:id`) usam o Cache API do Worker (`caches.default`, TTL 60 s, só respostas 200; **chave canônica (QA2-04)** = origem + caminho + só os parâmetros conhecidos da rota, em ordem fixa — `/groups`: `territory_id`; `/activities`: `bbox,territory_id,from,to,limit,cursor`; `/territories/search`: `q,limit`; rotas de detalhe: nenhum —, de modo que parâmetros extras ou fora de ordem caem na mesma entrada) além de `Cache-Control: public, max-age=60`. Respostas trazem `X-Cache: HIT|MISS`; num HIT o corpo (inclusive `meta.request_id`) é o da requisição que preencheu o cache, mas o header `X-Request-Id` é novo. Invalidação best-effort **só no colo atual**: `/activities/:id` após PATCH/cancelamento/moderação/suspensão/reativação; `/groups?territory_id=<território>` e `<município>` após aprovação/rejeição de proposta (QA2-03), PATCH, suspensão e reativação de grupo — e, quando o grupo é **municipal**, também `/groups?territory_id=<cada bairro do município>` (fallback, QA2-04). Outros colos e listas com bbox/datas/cursor expiram em até 60 s.

**Auth (Clerk, ADR 0005).** `Authorization: Bearer <session token do Clerk>` (JWT RS256 de 60 s obtido no front com `getToken()`). O Worker verifica com `verifyToken` de `@clerk/backend` (assinatura pelo JWKS da instância, cacheado no isolate; ou chave PEM em `CLERK_JWT_KEY` sem rede), `exp`/`nbf` (folga de 5 s; 60 s com `APP_ENV=local`), `sts = active`, **`iss` = Frontend API da instância** (QA3-04: `CLERK_ISSUER` ou derivado de `CLERK_PUBLISHABLE_KEY` — `pk_test_|pk_live_` + base64 de `<host>$`; sem emissor configurado só `local`/`test` aceitam), **`sub` no formato do contrato `ClerkUserId`** (`^user_[A-Za-z0-9]{1,64}$`) e `azp` ∈ `PUBLIC_ORIGIN` + `ALLOWED_ORIGINS` (token sem `azp` — emitido pela Backend API — só é aceito em `local`/`test`). Falha de rede/JWKS/configuração na verificação → 503 `SERVICE_UNAVAILABLE` (QA3-05), não 401. E-mail principal e verificação vêm das claims `email`/`email_verified` se o template de sessão as incluir; senão de `users.getUser` na Backend API, **com cache por isolate de 60 s** (QA3-01: até 500 entradas, LRU; invalidado em `PATCH /me` e no webhook `user.deleted`). Só o e-mail **principal** conta; conta sem principal → e-mail nulo (QA3-11). Usuário inexistente/banido → 401; Clerk com 429/5xx/sem resposta → 503. Rotas **sempre frescas** (sem cache e sem atalho de claims, cobrem banimento imediato — QA3-03): `POST /registrations` e `POST /admin/group-proposals/:id/reveal-contact`; nas demais, banimento/troca de e-mail no Clerk aparece em até 60 s (ou na vida do token, com claims). Não há sessão anônima nem provisória. Níveis:
- *sessão*: token Clerk válido (o e-mail pode ainda não estar verificado — na instância dev isso é impossível: o Clerk recusa e-mail principal não verificado);
- *organizador*: e-mail principal verificado no Clerk + perfil criado por `POST /registrations` com `email_verification_state = verified` e conta `active`. Se o e-mail principal mudou no Clerk (só vira principal depois de verificado), `profiles.email_contact` é ressincronizado e auditado (`profile.email_changed`, sem PII); se outro perfil já usa o endereço → 409 nas ações de organizador (em `GET /me` não: ver a rota);
- *admin*: e-mail principal verificado + id do Clerk em `app_private.admins` + perfil (se existir) **não suspenso** (QA3-06), em qualquer `APP_ENV`. **MFA não é exigido** (D35). Ver SECURITY.md.

Token ausente → 401; token inválido ou expirado → 401; nível insuficiente → 403 (`EMAIL_NOT_VERIFIED` ou `FORBIDDEN`); Clerk indisponível → 503 `SERVICE_UNAVAILABLE`.

**Limite de leitura autenticada (QA3-01).** Bucket `account_read`: 120 requisições/min por IP + id do Clerk em `GET /me`, `GET /my-activities` e **todas** as rotas `/admin/*` (aplicado depois de resolver a sessão e antes da checagem de admin/organizador).
